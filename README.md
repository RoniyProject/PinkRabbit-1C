# PinkRabbitMQ: внешняя компонента 1С для RabbitMQ

Внешняя компонента по технологии Native API для платформы 1С:Предприятие 8.3. Она позволяет из
встроенного языка 1С отправлять и получать сообщения через брокер
[RabbitMQ](https://www.rabbitmq.com/) по протоколу
[AMQP 0-9-1](https://www.rabbitmq.com/resources/specs/amqp0-9-1.pdf), в том числе по TLS.

Проект основан на [BITERP/PinkRabbitMQ](https://github.com/BITERP/PinkRabbitMQ), авторам исходной
компоненты - большое спасибо. Текущая версия - 2.3, список изменений - в [CHANGELOG.md](CHANGELOG.md).

## Возможности

- Подключение к RabbitMQ по TCP или TLS с проверкой сертификата сервера (на Windows).
- Объявление и удаление точек обмена (direct, fanout, topic, headers) и очередей, привязка очередей.
- Отправка сообщений с подтверждением брокера (publisher confirms): по одному или пачкой с одним
  ожиданием на всю пачку.
- Получение сообщений с ограничением числа неподтвержденных сообщений у клиента (prefetch), ручное и
  автоматическое подтверждение, возврат сообщения в очередь.
- Свойства сообщения AMQP (CorrelationId, ReplyTo, Expiration и другие), приоритет, заголовки в
  формате JSON.
- Контроль соединения: компонента сама отправляет heartbeat и сообщает о потере соединения
  исключением, а не пустым результатом.
- После подключения весь сетевой обмен выполняет отдельный поток компоненты. Методы, вызванные из
  1С, ждут результат с ограничением по времени.

## Поддерживаемые платформы

| Система | Разрядность платформы 1С | Файл в архиве | Как проверяется |
|---|---|---|---|
| Windows | 64 бит | `PinkRabbitMQ64.dll` | основной вариант: полный набор тестов, включая сценарии сбоев с тестовым брокером, запускается локально (см. [Тесты](#тесты)); в CI только собирается |
| Windows | 32 бит | `PinkRabbitMQ32.dll` | собирается из того же кода |
| Linux | 64 бит | `libPinkRabbitMQ64.so` | собирается в CI, там же запускаются тесты против RabbitMQ без сценариев сбоев и без TLS (переменная `PRMQ_TEST_SSL` в CI не задана); упавшие тесты не останавливают выпуск релиза |

Отличия версии для Linux:
- сертификат сервера при TLS не проверяется (см. [TLS](#tls));
- полуоткрытое соединение обнаруживается средствами TCP, без контроля входящего heartbeat (см.
  [Поведение при сбоях](#поведение-при-сбоях));
- имя хоста при `Connect` проверяется без ограничения по времени;
- `libPinkRabbitMQ64.so` из архива релиза собирается в CI на Ubuntu 22.04 и связана с glibc и
  libstdc++ динамически: ей нужны glibc 2.34 и libstdc++ с `GLIBCXX_3.4.29` (GCC 11) или новее. На
  системах со старой glibc (например Ubuntu 20.04, Debian 11) платформа не загрузит компоненту, в
  этом случае соберите библиотеку на целевой системе, см. [Linux](#linux). Требуемую версию glibc
  показывает команда `objdump -T libPinkRabbitMQ64.so | grep -o 'GLIBC_[0-9.]*' | sort -uV | tail -1`.

Архив компоненты содержит `MANIFEST.XML`, по которому платформа выбирает нужный файл. Веб-клиент
не поддерживается.

## Основные понятия RabbitMQ

Кратко о том, с чем работают методы компоненты:

- **Точка обмена** (exchange) принимает сообщения от отправителя и по правилам распределяет их по
  очередям. Тип точки определяет правило: `direct` - точное совпадение ключа маршрутизации,
  `topic` - совпадение по шаблону (`*` - одно слово, `#` - любое число слов), `fanout` - во все
  привязанные очереди, `headers` - по значениям заголовков.
- **Очередь** (queue) хранит сообщения до тех пор, пока их не получит и не подтвердит получатель.
- **Привязка** (binding) связывает точку обмена с очередью и задает ключ маршрутизации.
- **Ключ маршрутизации** (routing key) - строка, которую отправитель указывает для каждого
  сообщения. Точка обмена без имени (`""`) доставляет сообщение в очередь, имя которой совпадает с
  ключом маршрутизации.
- **Потребитель** (consumer) - подписка на очередь. Брокер сам присылает сообщения подписчику,
  компонента помещает их во внутренний кеш, из которого их по одному выдает метод
  `BasicConsumeMessage`.
- **Подтверждение** (ack) сообщает брокеру, что сообщение обработано и его можно удалить. Пока
  подтверждения нет, брокер считает сообщение неподтвержденным и при обрыве соединения доставит его
  снова.
- **Prefetch** (параметр `selectSize`) - сколько неподтвержденных сообщений брокер отдает одной
  подписке. Ограничивает объем памяти, который сообщения занимают у клиента.
- **Heartbeat** - периодический обмен короткими кадрами между клиентом и брокером. По ним обе
  стороны понимают, что соединение живо, даже когда сообщений нет.

## Установка и подключение

1. Скачайте архив релиза `PinkRabbitMQ_v<версия>.zip` на странице [Releases](../../releases) или
   соберите его сами, см. [Сборка из исходников](#сборка-из-исходников).
2. Загрузите архив в конфигурацию как общий макет с типом "Двоичные данные", например с именем
   `PinkRabbitMQ`.
3. Подключите компоненту и создайте объект:

```bsl
// результат подключения платформа кеширует на сеанс, повторный вызов не загружает компоненту заново
Если Не ПодключитьВнешнююКомпоненту("ОбщийМакет.PinkRabbitMQ", "BITERP", ТипВнешнейКомпоненты.Native) Тогда
    ВызватьИсключение "Не удалось подключить компоненту PinkRabbitMQ";
КонецЕсли;
Клиент = Новый("AddIn.BITERP.PinkRabbitMQ");
```

Второй параметр `ПодключитьВнешнююКомпоненту` (здесь `"BITERP"`) - имя подключения. Его выбирает
разработчик по правилам именования встроенного языка (буквы, цифры и подчеркивание, не начинается с
цифры), оно входит в имя объекта: `AddIn.<ИмяПодключения>.PinkRabbitMQ`.

**На клиенте** компоненту сначала пытаются подключить. Если `ПодключитьВнешнююКомпоненту` вернула
Ложь, ее устанавливают методом `УстановитьВнешнююКомпоненту("ОбщийМакет.PinkRabbitMQ")`
(пользователь подтверждает установку) и подключают снова. Если в конфигурации запрещены синхронные
вызовы, используйте `УстановитьВнешнююКомпонентуАсинх` и `ПодключитьВнешнююКомпонентуАсинх`.

**На сервере** (платформа 8.3.21 и выше) режим подключения задает четвертый параметр, компонента
допускает оба режима: изолированный и в процессе rphost. В изолированном режиме компонента работает в отдельном процессе, и ее аварийное завершение не
завершает рабочий процесс rphost со всеми сеансами; цена - межпроцессный вызов на каждое обращение к
компоненте. Чтобы режим не зависел от значения по умолчанию в конкретной версии платформы, указывайте
его явно:

```bsl
ПодключитьВнешнююКомпоненту("ОбщийМакет.PinkRabbitMQ", "BITERP",
    ТипВнешнейКомпоненты.Native, ТипПодключенияВнешнейКомпоненты.Изолированно);
```

**Варианты имени.** Кроме основного архива, релиз содержит архивы той же компоненты с другим именем
класса. Правило: из архива `PinkRabbitMQ<суффикс>_v<версия>.zip` объект создается как
`Новый("AddIn.<ИмяПодключения>.PinkRabbitMQ<суффикс>")`. Суффиксы: `_2` ... `_9`, `2`, `2_2` ...
`2_9`, `3`, `3_2` ... `3_9`. Например, из `PinkRabbitMQ2_2_v2.3.0.14.zip` объект создается как
`Новый("AddIn.BITERP.PinkRabbitMQ2_2")`. Файлы внутри всех архивов называются одинаково. Варианты
нужны, когда в одном процессе 1С должны работать разные версии компоненты.

## Быстрый старт

Отправить сообщение в очередь и прочитать его:

```bsl
ПодключитьВнешнююКомпоненту("ОбщийМакет.PinkRabbitMQ", "BITERP", ТипВнешнейКомпоненты.Native);
Клиент = Новый("AddIn.BITERP.PinkRabbitMQ");

Попытка

    // очередь "orders" сохраняется при перезапуске брокера (durable = Истина)

    Тег = 0;
    Пока Клиент.BasicConsumeMessage("", Тело, Тег, 3000) Цикл
        Сообщить("Получено: " + Тело);
        Клиент.BasicAck(Тег);
        Тело = "";
        Тег = 0;
    КонецЦикла;
    Клиент.BasicCancel(Потребитель);

    Сообщить(ОписаниеОшибки());
```

Схема с точкой обмена и привязкой:

```bsl
Клиент.DeclareExchange("events", "topic", Ложь, Истина, Ложь);
Клиент.DeclareQueue("events.orders", Ложь, Истина, Ложь, Ложь);
Клиент.BindQueue("events.orders", "events", "order.*");

// попадет в очередь events.orders: ключ совпадает с шаблоном order.*
Клиент.BasicPublish("events", "order.created", "{""id"": 1}", 0, Истина);
```

## Справочник

### Общие правила вызова

- **Ошибки.** Если метод не выполнился, в 1С вызывается исключение. Текст ошибки компоненты входит в
  `ОписаниеОшибки()`, платформа может дополнить его своим текстом. `GetLastError` возвращает текст
  компоненты без изменений, поэтому распознавать ситуацию надежнее по `GetLastError` или поиском
  подстроки в `ОписаниеОшибки()`. `GetLastError` нужно вызывать первым в блоке `Исключение`: вызов
  любого другого метода или обращение к свойствам сообщения очищает текст ошибки. Перечень - в
  разделе [Тексты ошибок](#тексты-ошибок).
- **Имена методов и свойств** пишите латиницей, как в справочнике: русских синонимов нет, а
  компонента сравнивает имя посимвольно, с учетом регистра.
- **Необязательные параметры** в сигнатурах указаны в квадратных скобках, их значения по умолчанию -
  в таблицах. Необязательный параметр можно не указывать или передать Неопределено.
- **Типы параметров** проверяются: в параметр типа Булево нельзя передать число, в строковый
  параметр - число или дату. Неверный тип вызывает исключение
  `Parameter <номер> expected type <тип>, but got <код типа>`: `<тип>` - `string`, `number` или
  `bool`, `<код типа>` - числовой код типа значения Native API (например 0 - Неопределено,
  11 - Булево, 22 - Строка). Параметры нумеруются с 0, при присваивании свойства номер всегда 0.
  Неопределено в обязательном строковом параметре считается пустой строкой. В обязательных
  параметрах `persist` метода `BasicPublish` и `autodelete` метода `DeclareExchange` Неопределено
  считается значением Ложь, исключения нет; в остальных обязательных параметрах типа Булево
  Неопределено вызывает исключение `Parameter <номер> expected type bool, but got 0`.
- **Единицы времени.** Таймаут `Connect` задается в секундах, таймауты `BasicConsumeMessage` и
  `WaitForConfirms` - в миллисекундах.
- **Строки** передаются брокеру в кодировке UTF-8.
- **Параметр arguments** у методов `DeclareExchange`, `DeclareQueue`, `BindQueue`, `BasicPublish`,
  `BasicConsume` - строка с объектом JSON. Пустая строка, `null` и `[]` означают "без аргументов".
  Некорректный JSON вызывает исключение `Wrong JSON in arguments: ...`, JSON не в виде объекта -
  `Arguments must be a JSON object`. Как значения превращаются в типы AMQP - в разделе
  [Тело, свойства и заголовки](#тело-свойства-и-заголовки-сообщений).
- **Один объект - одно соединение.** Объект компоненты используется из одного сеанса. Все подписки
  одного объекта работают через общий канал и общий кеш сообщений.

### Свойства

| Свойство | Тип | Доступ | Назначение |
|---|---|---|---|
| `Version` | Строка | чтение | Версия компоненты. У архивов со страницы Releases - `2.3.0.<номер запуска CI>`, у локальной сборки - значение параметра `VERSION`; без него (сборка решения в Visual Studio, сборка в Docker) - пустая строка, у цели `runTests` - `test` |
| `CorrelationId` | Строка | чтение и запись | Идентификатор для связи запроса и ответа |
| `MessageId` | Строка | чтение и запись | Идентификатор сообщения |
| `Type` | Строка | чтение и запись | Тип сообщения (произвольная строка приложения) |
| `AppId` | Строка | чтение и запись | Идентификатор приложения-отправителя |
| `ContentType` | Строка | чтение и запись | Тип содержимого, например `application/json` |
| `ContentEncoding` | Строка | чтение и запись | Кодировка содержимого, например `utf-8` или `gzip` |
| `UserId` | Строка | чтение и запись | Пользователь-отправитель. RabbitMQ принимает только логин текущего соединения |
| `ClusterId` | Строка | чтение и запись | Устаревшее поле AMQP, передается как есть |
| `Expiration` | Строка | чтение и запись | Время жизни сообщения в миллисекундах, записанное строкой, например `"60000"` |
| `ReplyTo` | Строка | чтение и запись | Имя очереди для ответа |

- **Запись** задает свойство для отправки. Значение применяется ко всем следующим вызовам
  `BasicPublish` этого объекта, пока его не изменят; пустая строка убирает свойство. Присваивать
  можно только строку или Неопределено. Число преобразуйте функцией `XMLСтрока()`: `Строка(60000)`
  возвращает `"60 000"` с разделителем групп разрядов, и брокер отвергнет такое значение
  `Expiration`. Уникальный идентификатор можно преобразовать и `Строка()`, и `XMLСтрока()`.
- **Чтение** возвращает значение из последнего сообщения, полученного методом
  `BasicConsumeMessage`.
- Если брокер отвергает значение (нечисловой `Expiration`, чужой `UserId`), ошибку сообщает
  `BasicPublish`, а при `waitConfirm` = Ложь - `WaitForConfirms`, см. ниже.

### Подключение

#### Connect

`Connect(host, port, login, pwd, vhost, [pingRate], [secure], [timeout])`

Устанавливает соединение с брокером. Если объект уже подключен, после проверки параметров прежнее
соединение закрывается и подписки сбрасываются, поэтому после ошибки подключения объект остается без
соединения. Ошибка в самих параметрах (неверный тип, пустое имя хоста, порт вне диапазона 1-65535)
прежнее соединение не затрагивает.

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `host` | Строка | | Имя или IP-адрес брокера. На Windows, если имени соответствует несколько адресов (например `::1` и `127.0.0.1` для `localhost`), компонента пробует их по очереди |
| `port` | Число | | Порт от 1 до 65535: обычно 5672 для AMQP и 5671 для AMQP по TLS |
| `login` | Строка | | Имя пользователя |
| `pwd` | Строка | | Пароль |
| `vhost` | Строка | | Виртуальный хост. У RabbitMQ стандартный виртуальный хост - `"/"` |
| `pingRate` | Число | 0 | Интервал heartbeat в секундах, от 0 до 65535 (значения вне диапазона приводятся к границе). 0 - принять интервал, предложенный брокером (у RabbitMQ 60 с), другое значение передается брокеру вместо предложенного |
| `secure` | Булево | Ложь | Подключаться по TLS, см. [TLS](#tls) |
| `timeout` | Число | 5 | Лимит времени в секундах, от 1 до 3600 (значения вне диапазона приводятся к границе). См. ниже |

Параметр `timeout`:
- **Подключение.** На Windows ограничивает подключение целиком: разрешение имени, TCP, TLS и вход
  AMQP. Исключение - TLS-рукопожатие: остаток лимита действует на каждую его операцию чтения и
  записи, поэтому брокер, который отвечает на рукопожатие медленно, может продлить `Connect` сверх
  `timeout`. Подключение, продленное так, все равно не устанавливается: если рукопожатие
  закончилось после истечения `timeout`, `Connect` завершается исключением `Connection timeout.`,
  если брокер не ответил на шаг рукопожатия за остаток лимита - исключением `Timeout`. При медленном
  TLS передавайте `timeout` больше.

  На Linux имя хоста сначала проверяется системным резолвером без ограничения по времени, лимит
  действует на ожидание остальных этапов. TCP-подключение к каждому адресу хоста библиотека
  AMQP-CPP дополнительно ограничивает 5 с, компонента этот лимит не меняет. Если `timeout` истек
  раньше, чем библиотека закончила попытки TCP-подключения, `Connect` ждет, пока она переберет все
  адреса хоста (до 5 с на адрес), и после этого завершается исключением `Connection timeout.`.
- **Операции.** Тот же лимит - время ожидания ответа брокера на каждую операцию, кроме
  `BasicConsumeMessage` и `WaitForConfirms` со своим таймаутом. Если ответ пришел в момент истечения
  лимита, компонента дожидается его обработки, но не дольше 30 с.

Ошибки подключения перечислены в разделе [Тексты ошибок](#тексты-ошибок).

#### IsConnected

`IsConnected() -> Булево`

Возвращает Истина, если соединение установлено и не потеряно. Брокеру ничего не отправляет,
поэтому вызов подходит для частой проверки.

### Точки обмена и очереди

#### DeclareExchange

`DeclareExchange(name, type, onlyCheckIfExists, durable, autodelete, [arguments])`

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `name` | Строка | | Имя точки обмена |
| `type` | Строка | | `"direct"`, `"fanout"`, `"topic"` или `"headers"`, строчными буквами. Другие типы (в том числе из плагинов RabbitMQ) не поддерживаются |
| `onlyCheckIfExists` | Булево | | Истина - не создавать, а проверить, что точка существует (иначе исключение) |
| `durable` | Булево | | Сохранять точку обмена при перезапуске брокера |
| `autodelete` | Булево | | Удалить точку, когда от нее отвязана последняя очередь |

поэтому точку обмена другого типа, например из плагина, можно проверить, передав `"direct"`.

### Отправка сообщений

#### BasicPublish

`BasicPublish(exchange, routingKey, message, livingTime, persist, [arguments], [waitConfirm])`

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `exchange` | Строка | | Имя точки обмена. `""` - доставка в очередь с именем, равным ключу маршрутизации |
| `routingKey` | Строка | | Ключ маршрутизации |
| `message` | Строка | | Тело сообщения |
| `livingTime` | Число | | Обязателен, но не используется: передавайте 0. Время жизни задается свойством `Expiration` |
| `persist` | Булево | | Истина - брокер сохраняет сообщение на диск (действует в durable-очередях) |
| `arguments` | Строка | `""` | Заголовки сообщения в формате JSON, например `{"source": "erp", "attempt": 1}` |
| `waitConfirm` | Булево | Истина | Истина - вернуть управление после подтверждения брокера. Ложь - только отправить, подтверждения дождаться позже методом `WaitForConfirms` |

К сообщению применяются установленные ранее свойства (`CorrelationId`, `ContentType` и т.д.) и
приоритет (`SetPriority`).

Что важно знать:
- При `waitConfirm` = Истина успешный вызов означает, что брокер принял сообщение. Запись на диск до
  подтверждения RabbitMQ гарантирует только для сообщения с `persist` = Истина, попавшего в
  durable-очередь.
- Сообщение, для которого у точки обмена нет подходящей очереди, брокер отбрасывает без ошибки и
  тоже подтверждает.
- Если точки обмена нет или брокер отверг свойства сообщения (нечисловой `Expiration`, чужой
  `UserId`), брокер закрывает канал отправки, и все отправленные ранее и еще не подтвержденные
  сообщения считаются неподтвержденными. Следующий `BasicPublish` открывает новый канал.
  - При `waitConfirm` = Истина вызов завершается исключением с текстом брокера.
  - При `waitConfirm` = Ложь сам вызов и следующие отправки, как правило, завершаются успешно, а
    ошибку сообщает только `WaitForConfirms` исключением
    `<N> message(s) were not confirmed by the broker: <текст брокера>`. Ошибка сохраняется до
    ближайшего вызова `WaitForConfirms`, даже если он выполнен после следующей пачки. N - число
    сообщений, которые брокер отклонил или которые остались без подтверждения при закрытии канала,
    среди всех отправленных с `waitConfirm` = Ложь после предыдущего вызова `WaitForConfirms`,
    который вернул Истина или вызвал исключение; текст после двоеточия - причина последней из этих
    неудач. Поэтому вызывайте `WaitForConfirms` после каждой пачки.
- Если брокер сообщил о нехватке ресурсов (`connection.blocked`, нехватка памяти или диска), метод
  сразу завершается ошибкой.
- Если метод завершился ошибкой таймаута, брокер мог все-таки принять сообщение: повторная отправка
  может дать дубль. Получатель должен уметь обрабатывать повторы.

#### WaitForConfirms

`WaitForConfirms([timeout]) -> Булево`

Ждет подтверждения всех сообщений, отправленных с `waitConfirm` = Ложь.

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `timeout` | Число | -1 | Время ожидания в миллисекундах, не меньше 20: значения от 0 до 19 дают ожидание до 20 мс. Отрицательное значение - таймаут из `Connect` |

Результат:
- **Истина** - все сообщения подтверждены.
- **Ложь** - время истекло. Неподтвержденные сообщения продолжают ждать, следующий вызов
  `WaitForConfirms` учтет и их, в том числе их ошибки.
- **Исключение** `<N> message(s) were not confirmed by the broker: <причина>` - брокер отклонил часть
  сообщений или канал отправки закрылся. Какие именно сообщения не подтверждены, компонента не
  сообщает, поэтому повторно отправляется вся пачка.
- **Исключение** `Connection lost: <причина>` - соединение потеряно до вызова. Если оно потеряно во
  время ожидания, исключение начинается с `<N> message(s) were not confirmed by the broker: `, а
  после двоеточия стоит `Connection lost: <причина>`, текст ошибки брокера (например
  `CONNECTION_FORCED - ...` при перезапуске брокера) или, на Linux при ошибке сокета, текст ошибки
  библиотеки AMQP-CPP. Потерю соединения надежно показывает
  `IsConnected()` = Ложь: тогда пачку отправляют повторно после нового `Connect`.

После нового `Connect` сведения о прежних отправках сбрасываются: все, что было отправлено с
`waitConfirm` = Ложь и не подтверждено успешным `WaitForConfirms`, нужно отправить повторно.

Пример пакетной отправки:

```bsl
Для Каждого Запись Из Пачка Цикл
    Клиент.MessageId = XMLСтрока(Запись.Идентификатор); // число без разделителя групп разрядов
    Клиент.BasicPublish("events", Запись.Ключ, Запись.Тело, 0, Истина, "", Ложь);
КонецЦикла;
Если Не Клиент.WaitForConfirms(30000) Тогда
    ВызватьИсключение "Брокер не подтвердил пачку за 30 секунд";
КонецЕсли;
// только теперь отправленные записи можно удалить из очереди исходящих в базе
```

Ограничение памяти: если неподтвержденных сообщений накопилось 10000 или их тела вместе с новым
превысят 64 МБ, очередной `BasicPublish` с `waitConfirm` = Ложь ждет подтверждения, как при Истина.

#### SetPriority

`SetPriority(priority)`

Задает приоритет для всех следующих отправляемых сообщений. 0 - без приоритета, значения меньше 0
считаются нулем, больше 255 - как 255. Приоритет учитывается только в очередях с аргументом
`x-max-priority`: его задает параметр `maxPriority` метода `DeclareQueue` или `arguments`.

### Получение сообщений

#### BasicConsume

`BasicConsume(queue, consumerId, noConfirm, exclusive, [selectSize], [arguments]) -> Строка`

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `queue` | Строка | | Имя очереди |
| `consumerId` | Строка | | Имя (тег) подписки. Пустая строка - имя сгенерирует брокер |
| `noConfirm` | Булево | | Истина - не требовать `BasicAck`, см. ниже |
| `exclusive` | Булево | | Истина - монопольно: пока подписка активна, у очереди не может быть других потребителей |
| `selectSize` | Число | 200 | Prefetch этой подписки: сколько сообщений может быть получено и не подтверждено (в кеше компоненты и уже выданных в 1С). 0 и меньше - 200, больше 2000 - 2000 |
| `arguments` | Строка | `""` | Аргументы подписки в формате JSON. Для stream-очередей `x-stream-offset`: `"first"`, `"last"`, `"next"`, целое число или дата вида `"2024-05-01T10:00:00+03:00"`. Секунды и смещение со знаком обязательны (например `+03:00`, для UTC `+00:00`), дробные секунды и обозначение `Z` не принимаются. Смещение записывайте с двоеточием: в записи без двоеточия минуты смещения отбрасываются без ошибки (`+0530` читается как `+05:00`) |

Возвращает имя подписки, которое нужно для `BasicCancel`. Подпискам одного объекта задавайте разные
имена или передавайте пустую строку: если `consumerId` совпадает с именем активной подписки этого
объекта, RabbitMQ закрывает соединение целиком (`NOT_ALLOWED - attempt to reuse consumer tag ...`),
и дальше методы сообщают `Connection lost: ...`.

**Ошибки подписки.** Перед подпиской компонента отдельным каналом проверяет, что очередь существует,
поэтому ошибка в имени очереди завершает только этот вызов. Пустое имя очереди не проверяется: ошибку
брокера на него получает общий канал подписок, как в случаях ниже. Для очереди с именем,
сгенерированным брокером, передавайте имя, которое вернул `DeclareQueue`. Остальные ошибки подписки
брокер сообщает закрытием общего канала подписок: например монопольная подписка на очередь, у которой уже есть потребители
(`ACCESS_REFUSED`), или недопустимые `arguments`. Тогда `BasicConsume` вызывает исключение с текстом
брокера, а остальные подписки объекта прекращаются: `BasicConsumeMessage` сообщит об этом
исключением `Consumer channel closed: ...`, нужные подписки создаются заново.

**noConfirm = Истина.** Компонента сама подтверждает сообщение в момент, когда
`BasicConsumeMessage` выдает его в 1С:
- `BasicAck` для такого сообщения можно не вызывать. Вызов допустим и ничего не делает для
  последних 16384 сообщений, выданных подписками с `noConfirm` = Истина. Для более старых `BasicAck`
  и `BasicReject` вызывают исключение `Delivery tag <N> is unknown or already acknowledged`, а если
  канал подписок с тех пор закрывался - `Delivery tag <N> is stale: ...`.
- `BasicReject` для такого сообщения вызывает исключение: оно уже подтверждено.
- Если соединение оборвется, пока сообщение лежит в кеше и еще не выдано в 1С, брокер доставит его
  повторно.
- Подтверждение отправляется без ожидания ответа брокера. Если соединение или канал подписок
  закроются сразу после выдачи сообщения в 1С, подтверждение может не дойти до брокера, и он
  доставит это сообщение повторно. Обработка и в этом режиме должна допускать повторы.

Подписка в этом режиме тоже работает с подтверждением, поэтому ограничение `selectSize` действует и
память процесса не переполняется.

**Как выбрать selectSize.** Сообщения, которые лежат в кеше компоненты, брокер считает
неподтвержденными. Если сообщение не подтверждено дольше `consumer_timeout` брокера (у RabbitMQ по
умолчанию 30 минут), брокер закрывает канал. Поэтому:
- `selectSize`, умноженный на время обработки одного сообщения, должен быть заметно меньше
  30 минут;
- `selectSize`, умноженный на размер сообщения, должен помещаться в память.

Для быстрой обработки небольших сообщений подходит 100-300, для медленной - 10-50.

#### BasicConsumeMessage

`BasicConsumeMessage(consumerId, outdata, messageTag, timeout) -> Булево`

| Параметр | Тип | Описание |
|---|---|---|
| `consumerId` | Строка | Не используется: сообщения всех подписок объекта приходят в общий кеш. Передавайте `""`. Имя подписки, которой доставлено сообщение, компонента не возвращает: чтобы обрабатывать очереди раздельно, используйте отдельный объект компоненты для каждой очереди |
| `outdata` | Строка | Выходной параметр: тело сообщения |
| `messageTag` | Число | Выходной параметр: тег сообщения для `BasicAck` и `BasicReject` |
| `timeout` | Число | Сколько ждать сообщения, в миллисекундах. Значение больше 7 суток сокращается до 7 суток, 0 и меньше - только проверить кеш без ожидания. Рекомендуется 1000-5000 |

Результат:
- **Истина** - сообщение получено: `outdata` и `messageTag` заполнены, а свойства сообщения и методы
  `GetHeaders`, `GetRoutingKey`, `GetPriority` относятся к нему.
- **Ложь** - за время ожидания сообщений не было. `outdata` получает значение Неопределено,
  `messageTag` - 0.
- **Исключение** (выходные параметры тоже очищаются):
  - соединение потеряно (обрыв сети, перезапуск брокера, нет heartbeat): `Connection lost: ...`;
  - брокер закрыл канал подписок: `Consumer channel closed: ...`;
  - подписок нет, и кеш пуст: `No active consumers`. Это же исключение возникает, когда брокер сам
    отменил последнюю подписку объекта (например очередь удалена) и полученные раньше сообщения
    закончились. Если у объекта остаются другие подписки, отмена одной из них брокером исключения не
    вызывает, а запись `Consumer cancelled <имя>` появляется в журнале только на уровне `I` и ниже.
    Чтобы такая отмена не осталась незамеченной, используйте отдельный объект компоненты для каждой
    очереди.

  Если библиотека AMQP-CPP сообщила о закрытии канала раньше, чем компонента обработала обрыв
  (такое бывает на Linux, а на Windows - когда ошибку обнаружила сама библиотека: при закрытии
  соединения брокером и при ошибке разбора полученных данных, например заголовков типов `x` и `s`),
  потеря соединения может прийти текстом `Consumer channel closed: ...`. Надежный признак потери соединения - `IsConnected()` =
  Ложь; в этом случае нужен новый `Connect`, как в примере в разделе
  [Работа на сервере 1С](#работа-на-сервере-1с).

Ожидание не нагружает процессор: поток сеанса спит, пока не придет сообщение или не истечет время.

#### BasicAck

`BasicAck(messageTag, [multiple])`

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `messageTag` | Число | | Тег из `BasicConsumeMessage` |
| `multiple` | Булево | Ложь | Истина - подтвердить также все предыдущие неподтвержденные сообщения этого объекта |

Подтверждение отправляется без ожидания ответа брокера. Исключение вызывается, если:
- тег равен 0;
- канал подписок был закрыт после получения сообщения (тег устарел): сообщение будет доставлено
  повторно, подтверждать его уже не нужно;
- тег неизвестен или уже подтвержден;
- соединение потеряно: обычно сообщается как устаревший тег, `Connection lost: ...` - только если
  обрыв произошел в момент вызова.

В первых трех случаях канал не закрывается, остальные сообщения можно подтверждать как обычно.
Для последних 16384 сообщений подписки с `noConfirm` = Истина `BasicAck` исключения не вызывает.

#### BasicReject

`BasicReject(messageTag, [requeue])`

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `messageTag` | Число | | Тег из `BasicConsumeMessage` |
| `requeue` | Булево | Ложь | Истина - вернуть сообщение в очередь для повторной доставки. Ложь - брокер удалит сообщение или отправит его в dead letter exchange очереди, если он настроен |

Исключения - те же, что у `BasicAck`, и дополнительно для сообщений подписки с `noConfirm` = Истина:
они уже подтверждены.

#### BasicCancel

`BasicCancel(consumerId)`

Отменяет подписку с указанным именем, `""` - все подписки объекта.
- Сообщения отмененной подписки, которые лежат в кеше и еще не выданы в 1С, возвращаются в очередь.
  Сообщения, уже выданные в 1С, можно подтверждать как обычно, если отмена прошла без таймаута (см.
  ниже).
- Если подписки с таким именем нет (при `""` - если у объекта нет ни одной подписки, например после
  обрыва соединения), вызывается исключение `Consumer not found`, при известной причине -
  `Consumer not found: <причина>`. Если во время отмены брокер закрыл канал подписок или
  соединение - `Cancel failed for <имя подписки>: <причина>`. Если соединение оборвалось (ошибка
  сокета, на Windows также нет heartbeat), на Windows приходит `Connection lost: <причина>`, на
  Linux обычно `Cancel failed for <имя подписки>: <причина>` с текстом ошибки библиотеки AMQP-CPP.
  Надежный признак потери соединения - `IsConnected()` = Ложь. В коде завершения работы
  оборачивайте вызов в `Попытка`.
- Если брокер не подтвердил отмену за таймаут `Connect`, компонента без исключения закрывает общий
  канал подписок. Прекращаются все подписки объекта, брокер возвращает в очередь и невыданные
  сообщения, и уже выданные в 1С, но не подтвержденные. Их теги устаревают: `BasicAck` и
  `BasicReject` для них вызывают исключение `Delivery tag <N> is stale: ...`.

#### GetRoutingKey

`GetRoutingKey() -> Строка` - ключ маршрутизации последнего полученного сообщения.

#### GetHeaders

`GetHeaders() -> Строка` - заголовки последнего полученного сообщения в формате JSON без пробелов.
Ключи упорядочены по возрастанию кодов символов Юникода с учетом регистра: заглавные латинские буквы
идут раньше строчных (`{"Z":1,"a":2}`), латиница раньше кириллицы. Например
`{"attempt":1,"source":"erp"}`. Без заголовков - `{}`.

Имена заголовков передаются как есть и могут содержать дефис: например, сообщению, пересланному в
dead letter exchange, RabbitMQ добавляет заголовок `x-death`. Такое имя не может быть ключом
структуры, поэтому разбирайте строку функцией `ПрочитатьJSON` с параметром `ПрочитатьВСоответствие`
= Истина, а не сравнением строк: при чтении в структуру (по умолчанию) такой заголовок вызовет
исключение.

```bsl
Чтение = Новый ЧтениеJSON;
Чтение.УстановитьСтроку(Клиент.GetHeaders());
Заголовки = ПрочитатьJSON(Чтение, Истина); // Соответствие, вложенные объекты тоже
Чтение.Закрыть();
```

#### GetPriority

`GetPriority() -> Число` - приоритет последнего полученного сообщения (0-255).

### Служебные методы

#### GetLastError

`GetLastError() -> Строка` - текст ошибки последнего вызова. Вызов любого другого метода и
обращение к свойствам сообщения сначала очищают этот текст, поэтому в блоке `Исключение` вызывайте
`GetLastError` первым. Повторный вызов `GetLastError` и чтение `Version` текст не меняют.

Текст очищается, только когда вызов дошел до компоненты. Если вызов отвергла сама платформа
(например из-за неверного числа параметров), `GetLastError` вернет текст прежней ошибки. Для
неизвестного имени метода или свойства `GetLastError` возвращает `Method not found: <имя>` или
`Property not found: <имя>`.

#### SetLogLevel

`SetLogLevel(level)`

Уровень журнала компоненты: строка `"D"` (отладка), `"I"` (информация), `"W"` (предупреждения, по
умолчанию), `"E"` (ошибки), `"F"` (критические) или число 0-4 в том же порядке (число вне диапазона
приводится к границе). Строка распознается по первой букве без учета регистра (подходят `"debug"`,
`"Error"`); пустая строка и неизвестная первая буква вызывают исключение `Unknown log level: ...`.
Записей уровня F компонента не создает, поэтому `"F"` отключает журнал полностью, в том числе запись
ошибок методов. Уровень действует на все объекты компоненты в процессе. См.
[Журнал компоненты](#журнал-компоненты).

#### SleepNative

`SleepNative(timeout)` - останавливает выполнение на указанное число миллисекунд. Для ожидания
сообщений используйте таймаут `BasicConsumeMessage`, а не этот метод.

### Тексты ошибок

Основные тексты исключений, по которым можно распознать ситуацию в коде 1С:

| Текст `GetLastError` (начало) | Метод | Причина |
|---|---|---|
| `Empty hostname not allowed` | `Connect` | Пустое имя хоста |
| `Wrong port: <порт>` | `Connect` | Порт вне диапазона 1-65535 |
| `Wrong hostname: <хост>` | `Connect` | Имя хоста не разрешается |
| `Connection timeout: host name ... was not resolved in time` | `Connect` | Имя хоста не разрешилось за `timeout` (Windows) |
| `Connection timeout.` | `Connect` | Подключение не завершилось за `timeout` |
| `TLS certificate of <хост> is rejected: ...` | `Connect` | Сертификат брокера не прошел проверку (Windows) |
| `Cannot load CA certificates from PINKRABBITMQ_TLS_CA_FILE=...` | `Connect` | Windows, `secure` = Истина: файл из переменной окружения не читается или не содержит сертификатов PEM |
| текст ошибки сокета или брокера | `Connect` | Отказ в соединении (на Windows `Connection refused`), неверный логин, пароль или vhost (`ACCESS_REFUSED - ...`, `NOT_ALLOWED - vhost ... not found`). На Windows TCP-подключение, не установленное за `timeout`, дает `Timeout: connect timed out: <адрес>`, а TLS-рукопожатие (`secure` = Истина), на шаг которого брокер не ответил за остаток `timeout`, - `Timeout` |
| `Connection is not established! Use the method Connect() first` | методы, которые обращаются к брокеру, кроме `BasicConsumeMessage` | `Connect` не вызывался или завершился ошибкой |
| `Connection lost: <причина>` | методы работы с брокером | Соединение потеряно. Если брокер закрыл соединение командой `connection.close` (например `CONNECTION_FORCED - ...` при штатной остановке или перезапуске), метод, который в этот момент ждал ответа брокера на свою команду, получает текст брокера без этого префикса. На Linux без префикса, с текстом ошибки библиотеки AMQP-CPP, завершается и метод, ждавший ответа при обрыве сети или закрытии TCP-соединения. Тексты `WaitForConfirms`, `BasicCancel` и `BasicConsumeMessage` в этих случаях описаны в их разделах: в частности, `BasicConsumeMessage` всегда сообщает `Connection lost: <причина>` или `Consumer channel closed: <причина>`. См. [Поведение при сбоях](#поведение-при-сбоях) |
| `AMQP server timeout error` | методы, ждущие ответа брокера | Брокер не ответил за `timeout` |
| `Exchange type not supported: <тип>` | `DeclareExchange` | Неподдерживаемый тип точки обмена |
| `Wrong JSON in arguments: ...`, `Arguments must be a JSON object` | методы с `arguments` | Ошибка в строке аргументов |
| `Arguments are nested too deep: <ключ>` | методы с `arguments` | Вложенность объектов и массивов JSON больше 64 уровней |
| `Wrong date format: ...` | `BasicConsume` | Неверная дата в `x-stream-offset` |
| `Unsupported json type for property x-stream-offset` | `BasicConsume` | Значение `x-stream-offset` не строка и не целое число |
| `Connection is blocked by the broker: <причина>` | `BasicPublish` | Брокеру не хватает памяти или диска |
| `Message was rejected by the broker (basic.nack)` | `BasicPublish` | Брокер отклонил сообщение |
| `<N> message(s) were not confirmed by the broker: ...` | `WaitForConfirms` | Часть пачки не подтверждена |
| `Consumer channel closed: <причина>` | `BasicConsumeMessage` | Брокер закрыл канал подписок. Тем же текстом может прийти потеря соединения, ее показывает `IsConnected()` = Ложь, см. [BasicConsumeMessage](#basicconsumemessage) |
| `No active consumers` | `BasicConsumeMessage` | Подписок нет и кеш пуст, в том числе до `Connect`. После `Connect`, завершенного ошибкой, вместо него может прийти `Connection lost: <причина>`: так бывает, если подключение отверг брокер (неверный логин, пароль или vhost), а на Linux и при других ошибках подключения, которые сообщила библиотека AMQP-CPP (отказ в TCP-подключении, `connection timed out`, ошибка TLS) |
| `Consumer not found` | `BasicCancel` | Подписки с таким именем нет |
| `Cancel failed for <имя подписки>: <причина>` | `BasicCancel` | Брокер закрыл канал подписок или соединение во время отмены; на Linux так же сообщается и обрыв соединения (на Windows при обрыве - `Connection lost: ...`) |
| `Message tag cannot be empty!` | `BasicAck`, `BasicReject` | Тег равен 0 |
| `Delivery tag <N> is stale: ...` | `BasicAck`, `BasicReject` | После получения сообщения канал подписок закрылся: его закрыл брокер, потеряно соединение, выполнен новый `Connect` или `BasicCancel` закрыл канал по таймауту отмены. Брокер доставит сообщение повторно |
| `Delivery tag <N> is unknown or already acknowledged` | `BasicAck`, `BasicReject` | Тег неизвестен или уже подтвержден |
| `Message <N> was acknowledged when it was received (noConfirm consumer), ...` | `BasicReject` | Сообщение подписки с `noConfirm` = Истина |
| `Unknown log level: ...` | `SetLogLevel` | Неизвестный уровень |
| `Parameter <номер> expected type <тип>, but got <код типа>` | любой | Неверный тип параметра, см. [Общие правила вызова](#общие-правила-вызова) |

Ошибки, которые вернул сам брокер (например `NOT_FOUND - no queue 'orders' in vhost '/'`,
`ACCESS_REFUSED - ...`, `PRECONDITION_FAILED - ...`), передаются как есть.

## Поведение при сбоях

| Ситуация | Что делает компонента | Что делать в 1С |
|---|---|---|
| Брокер недоступен при подключении | Если порт закрыт (служба брокера остановлена, отказ в соединении), `Connect` завершается ошибкой (на Windows `Connection refused`), не дожидаясь `timeout`: на Linux сразу, на Windows примерно через 1 с на каждый адрес хоста, потому что Windows повторяет попытку TCP-подключения после отказа (для `localhost` с адресами `::1` и `127.0.0.1` около 2 с). Если `timeout` не больше этого времени (например `timeout` = 1 для хоста с одним адресом или `timeout` = 2 для `localhost`), на Windows вместо отказа приходит `Timeout: connect timed out: <адрес>`. Если хост не отвечает, ошибка возникает примерно через `timeout`, на Windows его может превысить медленное TLS-рукопожатие. На Linux TCP-подключение к каждому адресу хоста дополнительно ограничивает библиотека AMQP-CPP (до 5 с на адрес, адреса перебираются по очереди): если библиотека закончила попытки со всеми адресами раньше, чем истек `timeout`, `Connect` завершается ее ошибкой `connection timed out` (примерно через 5 с на каждый неотвечающий адрес, для хоста с одним адресом - при `timeout` больше 5 с), иначе `Connect` после истечения `timeout` ждет, пока библиотека закончит попытки со всеми адресами, и завершается исключением `Connection timeout.`; к этому добавляется время проверки имени хоста | Повторить подключение с паузой |
| Обрыв сети, перезапуск брокера | Соединение помечается потерянным: `IsConnected` возвращает Ложь, методы работы с брокером вызывают исключение `Connection lost: ...` (`BasicCancel` - `Consumer not found: Connection lost: ...`, `BasicAck` и `BasicReject` сообщают об устаревшем теге). Если брокер закрыл соединение командой AMQP `connection.close` (так RabbitMQ поступает при штатной остановке и перезапуске), пока метод ждал его ответа (`DeclareExchange`, `DeclareQueue`, `BindQueue`, `BasicConsume`, `BasicPublish` с `waitConfirm` = Истина и другие), этот метод завершается текстом брокера без префикса, например `CONNECTION_FORCED - broker forced connection closure ...`. Если TCP-соединение закрыто без этой команды (например процесс брокера аварийно завершен), на Windows метод получает `Connection lost: ...`, например `Connection lost: Connection closed by server` или `Connection lost: Connection reset by peer`. На Linux в этом случае, как и при обрыве сети, метод получает текст ошибки библиотеки AMQP-CPP без префикса. Тексты `WaitForConfirms`, `BasicCancel` и `BasicConsumeMessage` в этом случае описаны в их разделах. Следующие вызовы сообщают `Connection lost: ...`. Надежный признак потери соединения - `IsConnected()` = Ложь | После паузы снова вызвать `Connect` и `BasicConsume` |
| Сеть пропала без разрыва TCP (полуоткрытое соединение) | Windows: соединение считается потерянным не позже чем через 2 интервала heartbeat без данных от брокера (при `pingRate` = 0 - 2 интервала брокера, у RabbitMQ 120 с), средства TCP могут обнаружить обрыв раньше. Если heartbeat отключен и в `Connect`, и на брокере, обрыв обнаруживают только средства TCP. На простаивающем соединении это keepalive: первая проба после 30 с без обмена данными, затем пробы каждые 5 с; число проб (10) задает Windows, поэтому обрыв обнаруживается примерно через 80 с без обмена данными. Если компонента отправляет данные (например `BasicPublish`, `BasicAck`), соединение закрывается, когда исчерпаны повторные передачи TCP; их число и интервалы задают настройки Windows. Linux: обрыв обнаруживает TCP: соединение закрывается, когда отправленные данные остаются без подтверждения 60 с, а на простаивающем соединении - когда от брокера 60 с не приходит никаких данных, в том числе ответов на пробы keepalive (пробы начинаются после 30 с без входящих данных); обычно в пределах 60-90 с после обрыва; точное время определяет ядро Linux | То же |
| Брокер закрыл канал подписок | `BasicConsumeMessage` вызывает исключение `Consumer channel closed: ...`, невыданные сообщения удаляются из кеша, брокер доставит их повторно. Тем же текстом может прийти и потеря соединения, см. [BasicConsumeMessage](#basicconsumemessage) | Заново вызвать `BasicConsume`; если `IsConnected()` = Ложь - сначала `Connect` |
| Брокер не ответил на операцию вовремя | Исключение `AMQP server timeout error`, операция могла выполниться. Исключения: `WaitForConfirms` возвращает Ложь, `BasicCancel` закрывает канал подписок без исключения, а подписку, которую брокер подтвердил после таймаута `BasicConsume`, компонента отменяет сама | Проверить результат или повторить. `BasicConsume` повторяют с пустым `consumerId` или с новым именем: подписка из вызова, завершившегося таймаутом, может остаться на брокере до повторного вызова, и повтор с тем же именем RabbitMQ отвергнет закрытием соединения (`NOT_ALLOWED`). Отправку повторяют с учетом возможного дубля |
| Брокеру не хватает памяти или диска (`connection.blocked`) | `BasicPublish` сразу завершается ошибкой | Повторить отправку позже |
| Сообщение отклонено брокером (nack) | `BasicPublish` или `WaitForConfirms` вызывает исключение | Отправить повторно |

После обрыва неподтвержденные сообщения брокер доставляет повторно. Обработчик сообщений должен
быть идемпотентным: повторная обработка того же сообщения не должна портить данные.

## Тело, свойства и заголовки сообщений

**Тело** передается в 1С как строка. Байты, не являющиеся корректным UTF-8, заменяются символом
U+FFFD, так же обрабатываются ключ маршрутизации и свойства. Двоичные данные передавайте в Base64.

Свойства `timestamp` и `delivery-mode`, имя точки обмена и признак повторной доставки
(`redelivered`) полученного сообщения компонента в 1С не передает. `timestamp` отправляемого
сообщения задать нельзя, `delivery-mode` задается параметром `persist`. Если получателю нужно время
отправки, передавайте его в заголовке.

**Заголовки при отправке** (параметр `arguments` у `BasicPublish`) задаются объектом JSON и
превращаются в типы полей AMQP так:

| Значение JSON | Тип поля AMQP | Примечание |
|---|---|---|
| целое число | `l` (знаковое 64 бит) | так его читают RabbitMQ и клиент Java. Целое больше 2^63-1 отправляется как `d` |
| дробное число | `D` (decimal) | если для какого-либо k от 0 до 6 число, умноженное на 10^k, отличается от целого не больше чем на 0,000001 и это целое умещается в знаковые 32 бита. Отправляется округленное значение: 12.5 - decimal 125 с 1 знаком после запятой, 2.0000004 - decimal 2, 0.0000001 - decimal 0. Если нужна точность выше, передавайте число строкой |
| дробное число | `d` (double) | во всех остальных случаях |
| строка | `S` | |
| Истина или Ложь | `t` | |
| null | `V` | |
| объект, массив | `F`, `A` | вложенность не больше 64 уровней, более глубокая вызывает исключение `Arguments are nested too deep: <ключ>` |

**Заголовки при получении** (`GetHeaders`) превращаются в JSON обратно: целые типы - в целые числа,
`D`, `d`, `f` - в дробные, `T` (время) - в целое число секунд, строки, логические значения и
вложенные таблицы и массивы - в соответствующие значения JSON, прочие типы - в `null`.
Ограничения при чтении:
- массивы длиннее 256 элементов обрезаются до 256;
- значения глубже 64 уровней вложенности превращаются в `null`;
- заголовки типов `x` (массив байтов) и `s` (short int в трактовке RabbitMQ; такие типы передает,
  например, клиент RabbitMQ для Java для значений `byte[]` и `Short`) используемая библиотека
  AMQP-CPP не разбирает. Возможны три исхода: значения искажаются, заголовок пропадает из результата
  `GetHeaders` без ошибки (так происходит с заголовком `x`, в котором пустой массив байтов), или
  соединение завершается ошибкой (на Windows `Consumer channel closed: frame out of range` или
  `Connection lost: frame out of range`).
  При ошибке соединения сообщение остается неподтвержденным: брокер возвращает его в очередь и после
  нового `Connect` доставляет снова, соединение обрывается при каждой попытке, и следующие за ним
  сообщения очереди компонента не получает. Такое сообщение удаляют из очереди средствами брокера,
  например в интерфейсе управления RabbitMQ. Не используйте эти типы в сообщениях для компоненты.

## TLS

Для подключения по TLS укажите `secure` = Истина и порт TLS брокера (обычно 5671). Клиентские
сертификаты не поддерживаются: на брокере не должна требоваться проверка сертификата клиента
(опции `ssl_options.verify` и `ssl_options.fail_if_no_peer_cert`, см.
[документацию RabbitMQ](https://www.rabbitmq.com/docs/ssl#peer-verification)).

**Windows.** Используются TLS 1.2 и 1.3. Сертификат брокера проверяется строго:
- цепочка должна вести к доверенному корневому сертификату;
- имя хоста из параметра `host` должно совпадать с сертификатом;
- ключ RSA не короче 2048 бит (или ECDSA), подпись сертификата брокера и промежуточных сертификатов
  не MD5 и не SHA-1 (подпись самого доверенного корневого сертификата не проверяется). Анонимные
  наборы шифров отключены.

Доверенными считаются сертификаты логического хранилища "Доверенные корневые центры сертификации"
учетной записи, от имени которой работает процесс (для сервера 1С - учетной записи службы). Windows
включает в него и сертификаты хранилища локального компьютера, поэтому корневой сертификат можно
установить в хранилище локального компьютера. Промежуточные сертификаты берутся из хранилища
"Промежуточные центры сертификации". Дополнительные доверенные сертификаты можно указать файлом PEM в
переменной окружения `PINKRABBITMQ_TLS_CA_FILE`. Для самоподписанного сертификата брокера достаточно
указать в этой переменной сам сертификат, требования к имени хоста и длине ключа при этом
остаются.

Компонента использует только сертификаты, уже установленные в хранилище, и не проверяет цепочку
средствами Windows. Корневые сертификаты публичных центров сертификации Windows обычно устанавливает
по требованию, когда цепочку к ним впервые проверяет сама Windows (например браузер). Поэтому на
сервере, где такой проверки не было, сертификат брокера от публичного центра сертификации может быть
отвергнут с `TLS certificate of <хост> is rejected`. В этом случае установите корневой сертификат в
хранилище явно или укажите его в `PINKRABBITMQ_TLS_CA_FILE`.

Сертификаты загружаются в общий для процесса набор. Набор загружается заново при первом `Connect` с
`secure` = Истина, выполненном через 60 минут после предыдущей загрузки или после смены пути в
`PINKRABBITMQ_TLS_CA_FILE`. Поэтому новый сертификат в хранилище Windows или новое содержимое файла по
прежнему пути начинают действовать не позже чем через час или после перезапуска процесса.
Переменная читается из окружения работающего процесса: новое системное значение действует только в
процессах, запущенных после изменения. Для сервера 1С это перезапуск службы; службы получают
окружение от диспетчера служб Windows, поэтому может потребоваться перезагрузка компьютера.

**Linux.** Сертификат брокера не проверяется, версии TLS задают настройки OpenSSL по умолчанию.
Используйте TLS на Linux только в доверенной сети. Подключение по TLS на Linux в CI не проверяется:
переменная `PRMQ_TEST_SSL` там не задана, поэтому тесты TLS из `test_util.py` пропускаются (включить
их можно и на Linux, см. [Тесты](#тесты)). Перед эксплуатацией проверьте `Connect` с `secure` =
Истина на целевой системе.

## Журнал компоненты

| | Windows | Linux |
|---|---|---|
| Каталог | `%LOCALAPPDATA%\biterp\logs` учетной записи процесса (для сервера 1С - учетной записи службы) | `~/.biterp/logs` пользователя, от имени которого работает процесс (для сервера 1С - пользователь службы, обычно `usr1cv8`) |
| Файлы | `comc1c<pid>-ГГГГ-ММ-ДД-ЧЧ-ММ.txt`, новый файл на каждую минуту, в которую была запись | так же |
| Формат | одна запись - одна строка JSON (дата, уровень, текст, версия компоненты) | так же |
| Хранение | при записи, не чаще раза в 10 минут, удаляются файлы старше 3 дней | так же |

Если каталог профиля определить не удалось, файлы журнала пишутся в текущий каталог процесса. Если
каталог журнала недоступен для записи, журнал не ведется, компонента об этом не сообщает.

По умолчанию пишутся только предупреждения и ошибки:
- каждая ошибка метода, переданная в 1С, записывается на уровне E;
- в момент обнаружения, без вызова из 1С, записываются потеря соединения
  (`Connection lost: <причина>`, E), закрытие канала подписок (`Consumer channel closed: <причина>`,
  W), блокировка и разблокировка соединения брокером (`Connection blocked by the broker: <причина>`,
  `Connection unblocked by the broker`, W). По ним можно установить время и причину обрыва. Запись
  `Connection lost` появляется и при неудачном `Connect`, если отказ пришел во время входа в брокер
  (неверный логин, пароль или vhost), а на Linux - при любой ошибке подключения, которую сообщила
  библиотека AMQP-CPP (отказ в TCP-подключении, `connection timed out`, ошибка TLS). При неверном
  имени хоста и при истечении `timeout` этой записи нет;
- таймаут отмены подписки в `BasicCancel` записывается как `Cancel timeout for consumer <имя>...`
  (E) вместе с `Consumer channel closed: Consumer cancel timeout` (W). Исключения в 1С в этом случае
  нет, поэтому запись в журнале - единственный след таймаута.

Записи уровней W и E сразу сбрасываются на диск, D и I - при очередной записи, если с прошлого
сброса прошло не меньше секунды.

Уровень задается методом `SetLogLevel` или переменной окружения `PINKRABBITMQ_LOG_LEVEL` (`D`, `I`,
`W`, `E`, `F`; распознается первая буква без учета регистра). Число и нераспознанное значение
переменной игнорируются без сообщения, остается уровень W. Переменная читается из окружения процесса
один раз, при первом создании объекта компоненты в процессе (об окружении службы - в разделе
[TLS](#tls)), `SetLogLevel` ее переопределяет. Уровень `D` пишет несколько строк на каждый вызов
метода: включайте его только на время диагностики. В изолированном режиме подключения `pid` в имени
файла - это процесс компоненты, а не rphost.

## Работа на сервере 1С

1. **Одно долгоживущее соединение.** Держите соединение в выделенном фоновом задании. Регламентное
   задание только проверяет, что это фоновое задание запущено, и запускает его при необходимости. Не
   подключайтесь на каждое сообщение: каждое подключение - это установка TCP и TLS, вход в брокер и
   отдельный поток в рабочем процессе.
2. **Отправка через очередь исходящих.** Пользовательские сеансы и транзакции проведения не должны
   обращаться к брокеру напрямую. Сообщения записываются в регистр сведений, а фоновое задание
   отправляет их пачками: `BasicPublish` с `waitConfirm` = Ложь и один `WaitForConfirms` на пачку.
3. **Цикл чтения.** `BasicConsumeMessage` с таймаутом 1000-5000 мс, без `SleepNative`. `BasicAck`
   сразу после успешной обработки, `BasicReject` при ошибке данных. Читайте только нужные свойства:
   каждое обращение к свойству - отдельный вызов компоненты.
4. **Восстановление после ошибки.** Запишите текст ошибки в журнал регистрации, выдержите паузу,
   увеличивая ее при повторных ошибках (5, 10, 20, 40, 60 с), и снова вызовите `Connect` на том же
   объекте: повторный вызов закрывает прежнее соединение. Можно и освободить объект
   (`Клиент = Неопределено`) и создать новый.
5. **Изолированный режим** (платформа 8.3.21 и выше): авария компоненты не завершит rphost со всеми
   сеансами. Цена - межпроцессный вызов на каждое обращение к компоненте.
6. **Наблюдение на брокере.** Соединение передает имя `1C PinkRabbitMQ <компьютер> pid <процесс>`,
   оно видно в интерфейсе управления RabbitMQ в поле connection name.

Пример фонового задания, которое читает очередь и восстанавливается после обрыва:


значение от предыдущей итерации, память под него может не освобождаться. После результата Ложь
компонента сама оставляет в них Неопределено и 0, поэтому повторный вызов без очистки допустим.

## Изменения по сравнению с версией 2.2

Вызовы, написанные для 2.2, совместимы по параметрам: новые параметры необязательные и добавлены в
конец, порядок старых сохранен. Но часть ситуаций, которые 2.2 пропускал без ошибки, теперь вызывает
исключение:
- потеря соединения в `BasicConsumeMessage`;
- повторный или устаревший тег в `BasicAck` и `BasicReject`, `BasicReject` для подписки с
  `noConfirm` = Истина;
- `arguments` в виде непустого массива или скалярного значения JSON;
- `Connect` с портом вне 1-65535 сразу вызывает `Wrong port: <порт>` (в 2.2 номер усекался до
  16 бит, и подключение шло на другой порт);
- `BasicPublish`, если брокер отклонил сообщение (`basic.nack`), например при переполнении очереди с
  аргументом `x-overflow` = `reject-publish`: 2.2 отправлял сообщение в транзакции AMQP, и брокер
  отбрасывал такое сообщение без ошибки, теперь вызывается исключение
  `Message was rejected by the broker (basic.nack)`;
- `Connect`, который длится дольше `timeout` (по умолчанию 5 с): в 2.2 `timeout` на подключение не
  действовал, теперь такое подключение завершается исключением таймаута. Текст зависит от этапа:
  `Connection timeout.`, на Windows также `Connection timeout: host name ... was not resolved in time`
  (разрешение имени), `Timeout: connect timed out: <адрес>` (TCP-подключение) и `Timeout` (брокер не
  ответил на шаг TLS-рукопожатия за остаток `timeout`), см. [Тексты ошибок](#тексты-ошибок). При
  медленной сети или TLS передавайте `timeout` больше.

Код, который вызывает эти методы без `Попытка`, нужно проверить.

| Было в 2.2 | Стало в 2.3 |
|---|---|
| `BasicPublish` открывал транзакцию AMQP на каждое сообщение | Используется подтверждение публикации (publisher confirms), отправка быстрее и меньше нагружает брокер. Добавлены `waitConfirm` и `WaitForConfirms` |
| `noConfirm` = Истина: брокер отдавал все сообщения очереди сразу, без ограничения | Сообщение подтверждается при выдаче в 1С, действует ограничение `selectSize` |
| `BasicAck` по устаревшему или уже подтвержденному тегу молча закрывал канал подписок | Вызывается исключение, канал продолжает работать. Добавлены `multiple` у `BasicAck` и `requeue` у `BasicReject` |
| Потеря соединения часто не обнаруживалась, `BasicConsumeMessage` бесконечно возвращал Ложь | Вызывается исключение `Connection lost: ...`. Добавлен `IsConnected` |
| Брокер закрывал простаивающее соединение через 1-2 минуты: heartbeat не отправлялся | Компонента отправляет heartbeat сама. На Linux начал действовать `pingRate` |
| `timeout` не влиял на подключение: разрешение имени не ограничивалось, на Windows не ограничивалось и TCP-подключение; вход AMQP (на Linux вместе с TCP-подключением) ждал фиксированные 15 с | `timeout` ограничивает подключение: на Windows все этапы, но медленное TLS-рукопожатие может продлить `Connect`; на Linux все этапы, кроме проверки имени хоста, но `Connect` могут продлить незавершенные попытки TCP-подключения библиотеки AMQP-CPP (до 5 с на адрес), см. [Connect](#connect) |
| Журнал на уровне отладки: несколько строк на каждый вызов метода, каждая запись сразу на диск; файлы хранились 10 минут | Уровень W по умолчанию, добавлен `SetLogLevel`; W и E сбрасываются на диск сразу, D и I - не чаще раза в секунду; файлы хранятся 3 дня |
| Целые числа в заголовках уходили типом `L`, который RabbitMQ не поддерживает; дробные - decimal с 6 знаками после запятой, знак отбрасывался (-1.5 уходило как 1.5), числа по модулю больше 4294.967295 искажались | Целые - `l`, дробные - decimal со знаком или double |
| `null`, объекты и массивы в `arguments` вызывали исключение; `GetHeaders` пропускал поля типов `d` и `f` (double, float), `V` (null), вложенные таблицы и массивы, decimal (`D`) читал без знака | Поддерживаются `null`, вложенные объекты и массивы, все числовые типы, кроме `s` (short int в трактовке RabbitMQ), см. [Тело, свойства и заголовки сообщений](#тело-свойства-и-заголовки-сообщений) |
| На Linux отправка, служебные операции и подписки шли через один канал: ошибка `BasicPublish` (например нет точки обмена), `DeclareQueue`, `BindQueue` и других служебных методов прекращала все подписки объекта | Отправка, служебные операции и подписки используют отдельные каналы: ошибка отправки или служебной операции подписки не затрагивает |
| Тело отправляемого сообщения обрезалось на первом символе с кодом 0 (`Символ(0)`) | Тело отправляется целиком |
| TLS на Windows: контекст создавался со строгой проверкой сертификата, но без доверенных корневых сертификатов (не загружались ни хранилище Windows, ни файл) | Доверенные корни - хранилище Windows и файл из `PINKRABBITMQ_TLS_CA_FILE`, TLS 1.2 и выше; сертификат с ключом RSA короче 2048 бит или подписью MD5, SHA-1 отвергается |
| `DeclareExchange` не поддерживал тип `headers` | Тип `headers` поддерживается |
| `DeclareQueue` с пустым именем возвращал пустую строку | Возвращается имя, сгенерированное брокером |
| `BasicConsume` с ошибкой в имени очереди закрывал канал подписок, прекращались все подписки объекта | Очередь проверяется отдельным каналом, ошибка затрагивает только этот вызов |
| `x-stream-offset` в виде строки всегда разбирался как дата | Принимаются также `"first"`, `"last"`, `"next"` |
| Тело не в UTF-8 вызывало исключение в `BasicConsumeMessage`, и сообщение в 1С не выдавалось: при `noConfirm` = Истина оно терялось, иначе оставалось неподтвержденным до закрытия канала. Свойство, ключ маршрутизации или заголовок не в UTF-8 вызывали исключение при чтении | Некорректные байты заменяются символом U+FFFD |
| `BasicCancel` не трогал кеш: невыданные сообщения отмененной подписки выдавались дальше, если у объекта оставались другие подписки, иначе оставались неподтвержденными до закрытия канала (при `noConfirm` = Истина терялись) | Невыданные сообщения отмененной подписки возвращаются в очередь |
| Теги сообщений начинались заново после переоткрытия канала | Теги растут в пределах объекта и не повторяются |

## Сборка из исходников

Готовые статические библиотеки зависимостей лежат в каталоге `lib`, заголовки - в `src`:

| Библиотека | Windows (`lib/win_Win32`, `lib/win_x64`) | Linux (`lib/linux`) |
|---|---|---|
| AMQP-CPP | есть | есть |
| POCO | 1.13.3 | не используется |
| OpenSSL | 3.3.0 | 3.0.13 |
| libevent | не используется | 2.1.12 |

### Windows

Нужны Visual Studio 2022 или Build Tools 2022 с компонентом "Разработка классических приложений на
C++" (набор инструментов v143) и Windows SDK. Команды выполняются в "Developer Command Prompt for
VS 2022": в обычной консоли `msbuild` нет в PATH.

Сборка архива релиза (32 и 64 бит, Release):

```cmd
cd windows
msbuild msbuild.xml -t:makeRelease -p:VERSION=2.3.0
```

- Результат: `package\PinkRabbitMQ32.dll`, `package\PinkRabbitMQ64.dll`, `package\version.txt` и
  архив `PinkRabbitMQ_v2.3.0.zip` в корне репозитория.
- Параметр `VERSION` нужно указывать всегда: он становится значением свойства `Version` и частью
  имени архива.
- В архив попадают все файлы каталога `package`, поэтому посторонние файлы из него нужно убрать
  заранее. Если архив с той же версией уже лежит в корне репозитория, его нужно удалить до сборки.
- `MANIFEST.XML` ссылается также на `libPinkRabbitMQ64.so`. Чтобы архив работал на сервере 1С под
  Linux, до `makeRelease` соберите библиотеку Linux (см. ниже) и положите `libPinkRabbitMQ64.so` в
  каталог `package`, как это делает CI.
- Параметр `-p:NAME_POSTFIX=2_2` собирает вариант с именем класса `PinkRabbitMQ2_2` (см.
  [Установка и подключение](#установка-и-подключение)). Имя архива при этом не меняется. Имя класса
  задается при сборке каждой библиотеки, поэтому `libPinkRabbitMQ64.so` для такого архива собирайте
  с тем же суффиксом (`-DNAME_POSTFIX=2_2`, как это делает CI): с библиотекой основного варианта
  объект `PinkRabbitMQ2_2` на Linux не создается.
- Только DLL, без архива: `msbuild msbuild.xml -t:FullRebuild -p:VERSION=2.3.0`.

Для разработки и тестов откройте `windows\WindowsAddin.sln`: проект `WindowsAddin` - компонента,
проект `tests` - тестовый стенд `python_test.dll`. Сборка решения в конфигурации Release x64
помещает компоненту и стенд в каталог `windows\x64\Release`, из которого запускаются тесты. Собрать
решение и запустить все тесты одной командой: `msbuild msbuild.xml -t:runTests` из каталога
`windows`. Этой команде нужен брокер на порту 5672, см. [Тесты](#тесты).

### Linux

```sh
mkdir linux/build
cd linux/build
cmake -DCMAKE_BUILD_TYPE=Release -DVERSION=2.3.0 ..
cmake --build .
```

Нужны CMake 3.16 и новее, компилятор C++17 со встроенной поддержкой `std::filesystem` (GCC 9 и
новее) и пакеты `build-essential`, `cmake` и `uuid-dev` (из него нужен заголовок `uuid/uuid.h`),
например `sudo apt install build-essential cmake uuid-dev`. OpenSSL, libevent и AMQP-CPP ставить не
нужно: библиотеки лежат в `lib/linux`, заголовки - в `src`. Результат - `libPinkRabbitMQ64.so` и тестовый стенд
`libpython_test.so` в каталоге `linux/build`. Вариант с другим именем класса: `-DNAME_POSTFIX=2_2`.

Вариант в Docker с брокером RabbitMQ для тестов: в каталоге `linux` выполнить
`docker compose up --build --abort-on-container-exit --exit-code-from prmq-build`. Контейнер
собирает отладочную сборку без `VERSION` в каталог `linux/tmp` и запускает тесты против брокера из
соседнего контейнера. Эта сборка предназначена только для тестов, для архива релиза используйте
сборку Release. Контейнер RabbitMQ публикует порт 5672 на машине, где запущен Docker: если порт занят
(например локальным RabbitMQ или `test/mock_broker.py`), освободите его перед запуском.

На Windows файл `linux/build.sh` должен остаться с концами строк LF: при `core.autocrlf=true`
(значение по умолчанию в Git for Windows) Git записывает его с CRLF, и bash в контейнере завершается
ошибками вида `$'\r': command not found`. Клонируйте репозиторий командой
`git clone -c core.autocrlf=input ...` или перед запуском преобразуйте `linux/build.sh` в LF.

### CI

Workflow `Entry` (`.github/workflows/entry.yml`) запускается при отправке изменений в `src`,
`windows`, `linux`, `test` или `.github` в любую ветку, а также вручную (Run workflow):
- собирает Linux и Windows для всех вариантов имени;
- на Linux для основного варианта имени выполняет тесты против RabbitMQ в контейнере (наборы с
  тестовым брокером на Linux не запускаются, тесты TLS пропускаются: переменная `PRMQ_TEST_SSL` не
  задана). Шаг тестов не останавливает сборку: упавшие тесты видны в аннотациях и сводке запуска;
- после всех сборок публикует один релиз `PinkRabbitMQ v2.3.0.<номер запуска>` со всеми архивами.
  Из ветки `main` выходит обычный релиз, из других веток - предварительный с пометкой `[DEV]`.

Версия задана в двух местах: `VERSION` в `.github/workflows/build.yml` и имя релиза в
`.github/workflows/entry.yml`, при смене версии их меняют вместе.

## Тесты

Тесты написаны на Python (pytest) и вызывают компоненту через тестовый стенд, который имитирует
платформу 1С. Они запускаются из каталога, где лежат компонента и стенд. Нужны Python 3 той же
разрядности, что и стенд, и пакет pytest (`python -m pip install pytest`), другие пакеты не нужны.
Для сборки Release x64 нужен 64-битный Python: 32-битный не загрузит `python_test.dll` и завершится
ошибкой `OSError: [WinError 193]`.

Windows (после сборки решения Release x64):

```cmd
cd windows\x64\Release
python -m pytest ..\..\..\test -v
```

Только наборы с тестовым брокером (живой RabbitMQ не нужен):

```cmd
cd windows\x64\Release
python -m pytest ..\..\..\test\test_stability.py ..\..\..\test\test_tls.py ..\..\..\test\test_review_fixes.py -v
```

Linux (после сборки в `linux/build`):

```sh
cd linux/build
python3 -m pytest ../../test -v
```

Наборы тестов:
- `test_stability.py`, `test_tls.py`, `test_review_fixes.py` работают со встроенным тестовым
  брокером `test/mock_broker.py`. Он имитирует сбои: обрыв и "зависание" соединения, закрытие
  канала, `connection.blocked`, задержку ответа. Живой RabbitMQ для них не нужен. Выполняются только
  на Windows. Для `test_tls.py` нужна утилита `openssl`: путь к ней берется из переменной окружения
  `OPENSSL`, затем из PATH, затем из стандартного каталога Git for Windows
  (`C:\Program Files\Git\usr\bin` или `C:\Program Files\Git\mingw64\bin`). Если утилита не найдена,
  эти тесты пропускаются.
- `test_amqp.py`, `test_util.py`, `test_ext.py` требуют брокер на порту 5672:
  - хост по умолчанию `127.0.0.1`, меняется переменной `RMQ_HOST` (порт не меняется);
  - логин и пароль по умолчанию `guest`, vhost `"/"`. Другие значения задаются файлом `test.conf` в
    каталоге запуска: объект JSON с ключами `host`, `login`, `password`, `vhost`, например
    `{"host": "rabbit.example.local", "login": "test", "password": "secret", "vhost": "/"}`. Ключ
    `host` из `test.conf` имеет приоритет над `RMQ_HOST`. Если указан `login` без `vhost`,
    виртуальным хостом становится значение `login`. Файл `windows/tests/test.conf.example` в этом
    формате не читается (разделы `amqp` и `amqps`, ключи `user` и `pwd`): с его копией тесты
    подключаются с параметрами по умолчанию. Стандартная установка RabbitMQ пускает пользователя
    `guest` только с localhost;
  - вместо RabbitMQ можно запустить тестовый брокер в отдельной консоли из корня репозитория:
    `python test/mock_broker.py --port 5672 --any-vhost`;
  - тесты TLS из этого набора включаются, если переменная `PRMQ_TEST_SSL` задана любым непустым
    значением (в том числе `0`), и подключаются к порту 5671; на
    Windows сертификат брокера должен быть доверенным и выдан на имя хоста.
